## Soroban patterns to use throughout

- **Storage:** instance keys for admin/config (`env.storage().instance()`);
  persistent keys for per-indicator records (`env.storage().persistent()`).
  New persistent entries must be TTL-managed — call `extend_ttl` on write or
  provide a maintenance function.
- **Auth:** every state-changing function calls `admin.require_auth()` and then
  re-verifies the caller matches the stored admin. Never skip the second check.
- **Errors:** prefer `#[contracterror]` enums over string panics for new code.
  Preserve existing `panic!("...")` messages exactly — tests assert on them.
- **Events:** emit `env.events().publish()` for every state change on new
  functions (`(publisher, hash, level, score)`).
- **Types:** `BytesN<32>` for hashes — raw addresses/domains NEVER go on-ledger.
- **Tests:** `#[cfg(test)] mod test` using `Env::default()`,
  `env.mock_all_auths()`, and generated clients (`SorobanThreatNetClient`).
  Test every auth path: happy path, non-admin, re-initialization.

## Contract specification (from SPEC.md)

Four functions only:

1. `initialize(admin: Address) -> ()` — auth `admin`; panic `"Already initialized"`
   if set; sets `Admin` and `TotalIndicators = 0`.
2. `publish_threat_indicator(admin: Address, indicator_hash: BytesN<32>, threat_level: ThreatLevel, reputation_score: u32) -> ()` —
   auth `admin` and `admin == Admin` (else panic `"Unauthorized admin"`);
   panic `"Reputation score must be between 0 and 100"` if `score > 100`;
   upsert record; increment total only on first insert.
3. `get_threat_indicator(indicator_hash: BytesN<32>) -> Option<IndicatorRecord>` — read-only.
4. `get_total_indicators() -> u32` — read-only.

Types: `ThreatLevel { Trusted=0, UnderInvestigation=1, Suspicious=2, ConfirmedMalicious=3 }`;
`IndicatorRecord { indicator_hash: BytesN<32>, threat_level: ThreatLevel, reputation_score: u32, updated_at: u64, verified_by: Address }`.
DataKeys: `Admin`, `Indicator(BytesN<32>)`, `TotalIndicators`.

See `SPEC.md` §5 for the known-gap list — if you implement a gap, update both
`SPEC.md` and this file's spec section in the same commit.

## Git workflow rules (non-negotiable)

1. **Never `git add .`** — stage specific files only.
2. **One commit per logical unit** (one function, one test block, one doc fix).
3. **Push immediately after every commit** — never batch.
4. **Conventional Commits:** `type(scope): description` with types
   `feat fix docs style refactor perf test build ci chore revert deps security`.
5. Never rewrite pushed history (`main` is protected on GitHub).

## Numbered build sequence (dependency order)

1. `chore: scaffold Cargo workspace` — Cargo.toml, `.gitignore`, rust-toolchain.
2. `ci: add contract test workflow` — `.github/workflows/ci.yml`.
3. `feat(contract): define types and DataKeys` — enums, structs, storage keys.
4. `feat(contract): implement initialize` + tests.
5. `feat(contract): implement publish_threat_indicator` + tests (all auth paths).
6. `feat(contract): implement get_threat_indicator and get_total_indicators` + tests.
7. `docs: write SPEC.md` and `docs: extend README`.
8. `chore: add deploy script` — `scripts/deploy.sh`.
9. `test: regenerate snapshots` — `cargo test` then commit `test_snapshots/`.

## Coding standards

- No `unwrap()` outside tests; use `expect` with a message or handle `None`.
- No floats anywhere — scores are `u32` basis points (0–100).
- `cargo fmt` and `cargo clippy -- -D warnings` must pass.
- `#![no_std]` — no std imports in contract code.
- Never store raw identifiers; only `BytesN<32>` hashes.
- Test messages must match existing panic strings exactly.
